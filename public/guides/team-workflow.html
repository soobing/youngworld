🤝 함께 만들기

개발자는 어떻게 함께 일할까?

브랜치를 따고 · PR을 올리고 · 코드리뷰를 받는 그 순서 그대로.
여러분이 개발하는 방식은 전 세계 개발자들이 일하는 방식과 동일합니다.

이 문서 하나로 끝내기 📖

Git이 뭔지 하나도 몰라도 괜찮아요. 등장인물 소개부터 시작해서, 실제로 손을 어떻게 움직이는지, 문제가 생기면 어떻게 하는지까지 순서대로 담았습니다. 헷갈릴 때마다 책장에서 다시 꺼내 보세요.

0. 왜 규칙이 필요할까 같은 파일, 두 사람

모둠 과제를 할 때 한 파일을 두 명이 동시에 고치면 어떻게 되죠? 나중에 저장한 사람이 앞사람 걸 덮어써 버립니다. 코드도 똑같아요. 아니, 더 심해요.

저장 버튼 하나로 3시간짜리 작업이 통째로 없어질 수 있어요. 그래서 규칙이 필요합니다.

코드가 더 심한 이유

발표 자료는 한 장 날아가도 눈으로 보면 압니다. 그런데 코드는 글자 한 줄만 어긋나도 게임이 아예 안 켜져요. 게다가 파일이 수십 개라 어디가 어긋났는지 눈으로 찾기 어렵습니다.

그래서 개발자들은 아주 단순한 약속 하나를 지킵니다 — "원본(main)에는 아무도 직접 손대지 않는다."

1. 등장인물 넷 이름부터 알고 가기

앞으로 계속 나올 단어는 딱 네 개예요. Git · GitHub · 브랜치 · PR. 지금은 "아 그런 거구나" 정도만 알고 넘어가도 충분해요. 뒤에서 직접 해 보면 저절로 이해됩니다.

Git
깃 · 내 컴퓨터에 깔리는 프로그램
코드가 언제 · 어떻게 바뀌었는지 전부 기록해 두는 타임머신. 잘못 고쳐도 예전으로 되돌릴 수 있어요.
🕹️ 세이브 기능이라고 생각하세요.
GitHub
깃허브 · 인터넷 웹사이트
내 컴퓨터에 있는 코드를 인터넷에 올려 친구들과 함께 보는 곳. 여러분이 계정을 만든 그 사이트예요.
☁️ 코드 전용 구글 드라이브라고 생각하세요.
브랜치 (branch)
브랜치 · '가지'라는 뜻
원본을 건드리지 않고 나 혼자 마음껏 고쳐보는 복사본. 다 되면 원본에 합칩니다.
🌿 연습용 사본이라고 생각하세요.
PR (Pull Request)
피알 · '합쳐 주세요' 요청
내 가지에서 만든 걸 원본에 합치기 전에 친구들에게 봐 달라고 내는 신청서.
📝 검사 맡기라고 생각하세요.

Git 과 GitHub 는 다른 거예요. 이름이 비슷해서 제일 많이 헷갈리는 부분!

Git은 내 노트북에서 도는 프로그램이고, GitHub는 그 결과물을 올려 두는 웹사이트예요. Git 없이도 GitHub는 볼 수 있고, 인터넷 없이도 Git은 씁니다. 서로 다른 물건입니다.

앞으로 나올 push(올리기)와 pull(받아오기)은 이 두 화살표예요. 방향만 반대입니다.

2. 전체 지도 한 장 이러한 과정으로 작업해요

우리가 한 일을 한 장으로 그리면 이렇습니다. 아래 7단계가 한 바퀴예요. 기능 하나 만들 때마다 이 바퀴를 한 번씩 돕니다.

① 최신 main 받기 → ② 가지 치기 → ③ 작업하며 커밋 → ④ 올리기(push) → ⑤ PR 올리기 → ⑥ 리뷰받고 고치기 → ⑦ 합치고 정리

게임으로 비유하면

main = 모두가 함께 쓰는 본서버. 브랜치 = 나 혼자 마음껏 실험하는 연습 서버. 커밋 = 세이브 포인트. PR = "제 연습 서버 결과를 본서버에 반영해 주세요" 하는 신청서. 코드리뷰 = 반영 전에 친구들이 같이 확인하는 것.

3. 한 바퀴 따라 하기 명령어 + Claude에게 시키는 말

각 단계마다 직접 치는 명령어와 Claude에게 시키는 말을 나란히 적어 뒀어요. 둘 다 결과는 같습니다. 명령어를 외울 필요는 없지만, 무슨 일이 일어나는지는 알고 시켜야 해요.

1최신 main 부터 받기

친구가 어제 올린 작업이 이미 main에 들어 있을 수 있어요. 낡은 main에서 가지를 치면 나중에 합칠 때 꼬입니다. 항상 여기서 시작!

# 원본 자리로 이동하고, 인터넷(GitHub)에서 최신 내용을 받아온다
git checkout main
git pull
🗣️CLAUDE에게 main 최신으로 받아줘

2내 가지(브랜치) 만들기

이제부터 뭘 부수든 main은 안전합니다. 이름은 "무슨 일을 하는 가지인지" 알 수 있게 지어요.

# -b 는 "새로 만들면서 그리로 이동" 이라는 뜻
git checkout -b feat/campfire-retro
앞에 붙이는 말언제실제 우리 저장소 예시
feat/새 기능을 만들 때feat/campfire-retro모닥불 기능 추가
fix/잘못된 걸 고칠 때fix/esc-closes-only-top-modalEsc 키 버그 수정
docs/설명·문서를 손볼 때docs/how-video-works-easier문서를 더 쉽게 고침

이름 짓기 3원칙

① 영어 소문자 + 붙임표(-) — 띄어쓰기와 한글은 쓰지 않아요. ② 무엇을 하는지가 보이게 — test, new, 수정 ❌ ③ 가지 하나엔 일 하나 — 모닥불도 만들고 버그도 고치면 리뷰하는 사람이 힘들어요.

🗣️CLAUDE에게 모닥불 기능 만들 거야. feat/campfire-retro 브랜치 만들어줘

3작업하고, 커밋(세이브)하기

커밋은 게임의 세이브 포인트예요. 잘 되던 지점에 자주 찍어두면, 망쳐도 거기로 돌아올 수 있어요. 한 가지 일을 끝낼 때마다 한 번씩 찍는 게 좋아요.

# 1) 바뀐 파일을 고르고  2) 이름표(메시지)를 붙여 저장
git add .
git commit -m "모닥불 켜지면 주변이 밝아지도록"
✗ 나중에 나를 괴롭히는 메시지

수정

ㅇㅇ

asdf

최종 진짜 최종

✓ 3개월 뒤에도 알아보는 메시지

모닥불 켜지면 주변이 밝아지도록

Esc 눌렀을 때 맨 위 창만 닫히게 수정

책장 문서 추가 — 함께 만드는 법

메시지 쓰는 요령: "무엇을 했다"보다 "무엇이 달라졌다"를 쓰세요. 파일 이름은 Git이 이미 기억하고 있으니 적을 필요 없어요.

🗣️CLAUDE에게 여기까지 커밋해줘 — 무엇이 바뀌었는지 보고 메시지까지 지어줍니다.

4GitHub에 올리기 (push)

여기까지는 전부 내 노트북 안에서만 일어난 일이에요. 친구들이 보려면 인터넷에 올려야 합니다. 노트북이 고장 나도 코드가 살아남는 순간이기도 해요.

# 이 가지를 처음 올릴 때 (-u 는 "앞으로 이 가지는 여기랑 짝" 이라는 표시)
git push -u origin feat/campfire-retro

# 두 번째부터는 이것만
git push
🗣️CLAUDE에게 올려줘(push)

5PR 올리기 — "(main 브랜치에) 합쳐도 될까요?"

push한 직후 GitHub 저장소에 들어가면 노란 띠에 「Compare & pull request」 버튼이 떠 있어요. 그걸 누르면 됩니다.

칸여기에 뭘 쓰나
제목한 줄 요약. 커밋 메시지처럼.예) 모닥불에 레트로 감성 불빛 추가
본문아래 3줄이면 충분해요.
Assignees담당자 나 자신을 넣습니다. "이 작업은 제가 맡고 있어요"라는 표시예요. 오른쪽 사이드바 Assignees → 톱니바퀴(⚙️) 클릭 → 내 이름 선택. assign yourself 를 눌러도 돼요.
Reviewers리뷰어 봐 줬으면 하는 사람을 넣습니다. 선생님이나 친구요. 지정하면 그 사람에게 알림이 갑니다. 안 넣으면 아무도 모르고 지나갈 수 있어요.
PR 작성 화면 오른쪽 사이드바에 있어요. 톱니바퀴(⚙️)를 눌러서 사람을 고릅니다.

Assignee 와 Reviewer, 뭐가 다른가요? 🤔

Assignee = 이 일을 하는 사람 (= 나). Reviewer = 이 일을 봐 주는 사람 (= 친구·선생님). 역할이 반대예요.

둘 다 안 넣어도 PR은 올라갑니다. 그래도 넣는 이유는 — PR이 여러 개 쌓였을 때 누구 것인지 한눈에 보이고, 리뷰어에게 알림이 가서 기다리는 시간이 줄어들어요.

## 무엇을 했나요
광장 가운데에 모닥불을 놓고, 밤이 되면 주변이 노랗게 밝아지게 했어요.

## 왜 했나요
밤에 광장이 너무 어두워서 친구들이 어디 있는지 안 보였어요.

## 봐주세요
불빛 크기가 적당한지, 반짝이는 속도가 너무 빠르지 않은지 봐주세요!

"봐주세요"를 꼭 쓰세요. 리뷰하는 친구가 어디를 볼지 알면 리뷰가 훨씬 빨라지고 좋아져요. 자신 없는 부분을 솔직히 적는 게 오히려 프로답습니다.

🗣️CLAUDE에게 PR 올려줘 — 바뀐 내용을 읽고 제목·본문까지 써 줍니다. 올린 뒤 내가 직접 읽어보고 고치면 더 좋아요.

6코드리뷰 받고 고치기

리뷰는 시험 채점이 아니에요. 나 혼자 못 본 걸 한 사람 더 봐주는 것뿐입니다. 실제로 실무에서도 PR 하나에 리뷰 몇 번 오가는 게 보통이에요.

고쳐 달라는 말을 들었다면? 새 PR을 만들 필요가 전혀 없어요. 같은 브랜치에서 고치고 커밋 → push 하면, 열려 있던 PR이 자동으로 갱신됩니다.

git add .
git commit -m "리뷰 반영 — 불빛 크기 줄이고 깜빡임 느리게"
git push   # PR 페이지를 새로고침하면 바뀐 게 반영돼 있어요

7합치고(merge) 뒷정리

리뷰가 통과되면 PR 페이지의 초록색 Merge 버튼을 누릅니다. 이 순간 내 작업이 main의 일부가 돼요. 🎉

# 합쳐진 결과를 내 노트북에도 받아오고, 다 쓴 가지는 정리한다
git checkout main
git pull
git branch -d feat/campfire-retro

브랜치를 지워도 작업은 안 사라져요. 이미 main 안에 들어갔으니까요. 가지는 일회용 작업대라고 생각하면 됩니다. 다음 기능은 새 가지에서!

4. 충돌(conflict)이 났다면 해결하면 됩니다.

두 사람이 같은 파일의 같은 줄을 고쳤을 때 Git이 멈춰 서서 이렇게 말합니다 — "둘 중 어느 걸 쓸까요?" 이게 충돌이에요. 에러가 아니라 질문입니다.

우리 저장소에서 진짜 있었던 일 🙋

「나의 꿈은」 영상을 만들 때, 학생 목록(STUDENT_DREAMS)에 최승찬 학생과 안해찬 학생이 각자 자기 줄을 같은 위치에 추가했어요. 둘 다 맞는 작업인데 위치가 겹쳐서 충돌이 났습니다. 답은? 둘 다 남기기. 그게 끝이었어요.

충돌이 나면 파일 안에 이런 표시가 생겨요. 겁먹지 말고 천천히 읽으면 됩니다.

<<<<<<< HEAD            ← 여기부터는 "내가 쓴 것"
  { name: '안해찬', ... },
=======                    ← 경계선
  { name: '최승찬', ... },
>>>>>>> main            ← 여기까지는 "상대가 쓴 것"
  • 1단계 — 어느 쪽을 남길지 정한다. (둘 다 남기는 경우도 아주 많아요!)
  • 2단계 — <<<<<<< · ======= · >>>>>>> 세 줄을 지운다. 이 표시는 사람 보라고 넣은 거라 코드가 아니에요.
  • 3단계 — 게임을 켜서 정말 잘 돌아가는지 확인하고 커밋한다.

충돌났을 때 절대 하지 말 것 ⛔

당황해서 폴더를 통째로 지우고 다시 받는 것. 그러면 진짜로 작업이 날아갑니다. 충돌은 고장이 아니라 질문이에요. 답만 해 주면 바로 이어서 할 수 있어요.

🗣️CLAUDE에게 충돌 났어. 어디가 부딪혔는지 설명해주고, 둘 다 살리는 방향으로 정리해줘 — 이때 "알아서 해줘"보다 어느 쪽을 원하는지 말해주는 게 훨씬 정확해요.

5. 리뷰를 주고받는 태도 사람 이야기

기술보다 이게 어려워요. 내 코드에 지적을 받으면 기분이 이상하거든요. 그래서 개발자들 사이엔 딱 하나의 약속이 있습니다 — 사람을 말하지 말고, 코드를 말하기.

✗ 이렇게 쓰면 서로 힘들어요

"이거 왜 이렇게 짰어?"

"이건 좀 아닌 듯"

"기본도 모르네ㅋㅋ"

"너 때문에 내꺼 충돌 났잖아"

→ 사람을 평가하고 있어요. 충돌은 누구의 잘못도 아닌데 말이죠.

✓ 이렇게 쓰면 같이 좋아져요

"여기 이름을 lightOn으로 하면 뜻이 더 잘 보일 것 같아요!"

"불빛이 밤에만 켜지는 건가요? 낮에도 켜지면 어떻게 되나요?"

"모닥불 반짝임 진짜 예쁘다 👏"

"제가 충돌을 해결했으니 머지해도 좋을 것 같아요!"

→ 코드를 두고 이야기하고 있어요.

이럴 땐이렇게
고쳤으면 하는 게 있을 때질문 형태로. "~하면 어떨까요?"내가 잘못 이해했을 수도 있으니까요. 실제로 그런 경우 많아요.
좋은 걸 발견했을 때말해주기. 칭찬은 리뷰의 절반이에요."여기 정리 깔끔하다" 한 줄이 다음 PR을 만들게 합니다.
리뷰를 받았을 때고치든 안 고치든 답을 남기기."고쳤어요" / "이건 이래서 그대로 뒀어요" — 안 고치는 것도 정당한 답이에요.
의견이 갈릴 때둘 다 맞을 수 있어요. 이유를 한 번씩 설명하고 안 되면 선생님 호출!

6. 이 방식이 세상을 만들었다 오픈소스

지금까지 배운 걸 다시 볼까요. 가지를 치고 · PR을 올리고 · 리뷰를 받고 · 합친다. 우리는 이걸 여섯 명이 했어요. 그런데 전 세계 수만 명이 똑같은 방식으로 만드는 프로그램들이 있습니다. 그걸 오픈소스(Open Source)라고 불러요.

오픈소스는 프로그램의 설계도(소스 코드)를 통째로 공개해서, 누구나 보고 · 쓰고 · 고치고 · 나눌 수 있게 하는 문화예요. 여러분의 코드가 GitHub에 올라가 있는 것처럼요.

모르는 사람들이 조금씩 기여(contribution) 해서, 혼자서는 절대 못 만들 물건이 만들어져요.
🔍 열려 있어요
어떻게 만들었는지 안을 들여다볼 수 있어요. 궁금하면 코드를 직접 열어 보고 배웁니다.
🤝 같이 만들어요
고칠 곳을 발견하면 PR을 보냅니다. 여러분이 우리 저장소에 한 것과 완전히 똑같은 방법으로요.
🎁 나눌수록 커져요
내가 나눈 걸 다른 사람이 이어서 더 좋게 만들어요. 써도 줄어들지 않는 신기한 물건입니다.
🙏 감사와 규칙
공짜라고 막 쓰면 안 돼요. 라이선스라는 사용 규칙이 있고, 만든 사람을 밝혀 주는 것이 예의예요.

우리 게임도 오픈소스를 활용 했어요 🌏

영월드는 우리가 처음부터 다 만든 게 아니에요. 이미 누군가 무료로 공개해 둔 도구들 위에 우리 코드를 얹은 겁니다.

전부 무료입니다. 그리고 전부 이 문서에 나온 방식으로 만들어졌어요.

세계 어딘가의 사람이 가지를 치고, PR을 올리고, 모르는 사람에게 리뷰를 받고, 합쳐서 — 그렇게 쌓인 게 지금 여러분 노트북에서 돌아가고 있는 겁니다.

여러분도 이미 그 세계 안에 있어요 ✨

우리 저장소도 GitHub에 공개돼 있어요. 지구 반대편 누군가가 여러분의 코드를 볼 수 있다는 뜻입니다. 언젠가 좋아하는 프로그램에서 이상한 점을 발견하면, 여러분도 PR을 보낼 수 있어요. 방법은 이미 다 배웠으니까요. 나이도, 자격증도, 회사도 안 물어봅니다. 코드만 봅니다.

7. 한 장 치트시트 막힐 때 여기만 보기

하고 싶은 것명령어Claude에게
최신 main 받기git checkout main → git pull"main 최신으로 받아줘"
새 가지 만들기git checkout -b feat/이름"○○ 만들 브랜치 따줘"
지금 어디인지 확인git status"지금 상태 알려줘"
세이브(커밋)git add . → git commit -m "...""여기까지 커밋해줘"
GitHub에 올리기git push 처음엔 git push -u origin 브랜치이름"올려줘"
PR 올리기GitHub의 Compare & pull request 버튼"PR 올려줘"
합친 뒤 정리git pull → git branch -d 브랜치이름"머지됐어, 정리해줘"

자주 겪는 상황 🛟

이런 일이 생겼다면이렇게 하세요
실수로 main에서 그냥 작업해 버렸어요 아직 커밋 안 했다면 지금 git checkout -b feat/이름 하세요. 바뀐 내용이 새 가지로 그대로 따라옵니다. 아무 일도 안 일어나요!
push 했더니 거절당했어요 내가 없는 사이 main이 앞서갔다는 뜻. git pull 로 받아온 뒤 다시 push.
PR을 올렸는데 바꿀 게 생겼어요 새 PR 만들지 마세요. 같은 브랜치에 커밋 + push 하면 PR이 자동으로 갱신됩니다.
충돌(conflict)이 났어요 고장 아니에요. 4장으로 돌아가서 세 줄만 지우고 어느 쪽을 남길지 정하면 끝.
뭘 잘못한 것 같아 무서워요 😰 Git은 커밋한 건 웬만해선 안 지웁니다. 폴더를 지우는 것만 빼면 대부분 되돌릴 수 있어요. Claude에게 지금 상태 설명해줘 부터 시키세요.

마무리 — 여러분이 이미 한 일

  • ✅ Git을 설치하고 GitHub 계정을 만들었다
  • ✅ main에서 내 브랜치를 따서 안전하게 작업했다
  • ✅ 작업을 커밋하고 push 해서 인터넷에 올렸다
  • ✅ PR을 올려 "합쳐도 될까요?" 하고 물었다
  • ✅ 친구·선생님의 코드리뷰를 받고 반영했다
  • ✅ 내 코드가 main의 일부가 되는 걸 봤다
  • ✅ 전 세계가 똑같은 방식(오픈소스) 으로 만든다는 걸 알았다

이게 전부입니다. 진짜로요.

구글도, 넷플릭스도, 여러분이 쓰는 앱을 만드는 회사도 매일 이 바퀴를 돌립니다. 규모만 다를 뿐 순서는 똑같아요.

혼자 만들면 내가 아는 만큼만 나옵니다. 같이 만들면 서로가 못 본 걸 봐 주기 때문에 둘 다보다 더 나은 게 나와요. 그게 협업을 하는 진짜 이유예요.
